# Repository Guidelines

## Структура проекта

Это Android-приложение с единственным модулем `app`. Исходный код расположен в `app/src/main/java/ru/mgusev/eldritchhorror/`: API-клиенты — в `api`, модели — в `model`, доступ к данным — в `repository` и `database`, DI — в `di`, экраны и их логику — в `ui` и `presentation`. Android-ресурсы находятся в `app/src/main/res`, статическая база — в `app/src/main/assets/databases/StaticDataDB.db`.

Юнит-тесты хранятся в `app/src/test`, инструментальные — в `app/src/androidTest`. Общие графические исходники и экспортированные изображения находятся в `images/`; не переносите их в ресурсы без необходимости.

## Сборка, тесты и запуск

На Windows используйте Gradle Wrapper из корня репозитория:

```powershell
.\gradlew.bat assembleDebug          # собрать отладочный APK
.\gradlew.bat test                   # запустить локальные JUnit-тесты
.\gradlew.bat connectedAndroidTest   # запустить Espresso-тесты на устройстве/эмуляторе
.\gradlew.bat clean                  # удалить результаты сборки
```

Для запуска из Android Studio откройте корневой каталог и выберите конфигурацию `app`. Локальный SDK задаётся в `local.properties`; этот файл не коммитится. Проект использует compile/target SDK 30 и Java 8.

## Стиль кода и именование

Следуйте стилю существующих Java- и Kotlin-файлов: отступ в четыре пробела, фигурная скобка на той же строке, один публичный тип на файл. Имена классов — `PascalCase`, методов и полей — `camelCase`, констант — `UPPER_SNAKE_CASE`. Сохраняйте пакетную структуру по ответственности; новый экран и его ресурсы называйте согласованно, например `GameDetailActivity` и `activity_game_detail.xml`.

Линтер или автоформаттер не настроены: перед отправкой вручную проверьте импорт, форматирование и отсутствие неиспользуемого кода. Не меняйте сгенерированные каталоги `build/` или `.gradle/`.

## Тестирование

Добавляйте JUnit-тесты для изолированной логики в `app/src/test` с именами вида `ThingTest`; UI-сценарии, требующие Android framework, размещайте в `app/src/androidTest`. Тест должен описывать поведение, например `loadsCachedItemsWhenNetworkFails`. Перед PR запустите минимум `.\gradlew.bat test`; для изменений UI проверьте экран на устройстве или эмуляторе.

## Коммиты и pull request’ы

В истории встречаются короткие изменения и релизные сообщения (`build 58 v.2.5.5`), а также русские описательные коммиты. Используйте короткое повелительное описание, например `Исправить загрузку карточек`; отделяйте несвязанные изменения. В PR укажите цель, затронутые экраны/данные, способ проверки и ссылку на задачу. Для визуальных изменений приложите скриншоты; отдельно отметьте изменения базы, ресурсов или локализаций.
